## 1. Целевая модель (как должно быть по продукту)

Зафиксировано владельцем и в целом отражено в пользовательских документах:

1. EList — **площадка**, не продавец билетов и не организатор мероприятия.
2. **Продавец** — организация-организатор; договор на посещение — между покупателем и организатором.
3. Оплата через **ЮKassa**: деньги (доля продавца) идут на **реквизиты организатора**; сервис удерживает **свой процент через split** при проведении платежа.
4. Кошелёк платформы к билетам **не относится** (только тариф).

## 2. Что говорят исходники документов

### Согласовано с целевой моделью

| Документ | Формулировка |
|----------|--------------|
| **Пользовательское соглашение** §6.1 | Продавец — Организатор; Сервис — посредник, **не продавец**; договор посещения — между Пользователем и Организатором |
| **Пользовательское соглашение** §6.2 | Продажа на основании договора (агентского или иного) с Организатором; цена не выше цены Организатора |
| **Соглашение для организаций** §2.2 | Сервис — информационный посредник/агрегатор; Оператор **не организатор** мероприятий |
| **Соглашение для организаций** §2.4 | При продаже билетов продавец — Организатор; Сервис — посредник и канал распространения, **не продавец** |
| **Агентский договор** §5.1 | Оплата через Провайдера **с разделением платежа**: доля Принципала → его счёт (реквизиты выплат), вознаграждение Агента → Агенту |
| **Агентский договор** §5.2 | Деньги Принципала **не являются выручкой** Агента |
| **Агентский договор** §9 | Ответственность за мероприятие — на Принципале |

Это хорошо стыкуется со схемой «площадка + split ЮKassa».

### Policy / Consent (не про билеты, но важно)

| Документ | Вывод |
|----------|--------|
| **Политика** | Информационный документ (ст. 18.1 152-ФЗ). В тексте: использование сервиса = согласие с Политикой **в объёме, не требующем отдельного согласия**; отдельные цели — через Согласие. |

## 3. Расхождения и «заковырки» в Агентском договоре

### 3.1. Незакрытая развилка §2.1 (критично)

В предмете договора оставлена альтернатива в квадратных скобках:

> …реализации Билетов … через Сервис **[от имени и за счёт Принципала / от своего имени за счёт Принципала]**

Это два разных режима:

| Вариант | Смысл | Близость к заявленной схеме |
|---------|--------|-----------------------------|
| От **имени и за счёт** Принципала | Раскрытое агентирование: покупатель видит продавца-организатора | Ближе к «продавец = организатор» + split на его реквизиты |
| От **своего имени за счёт** Принципала | Комиссионер: формально продаёт Агент (площадка) | Хуже стыкуется с ПС/Org («сервис не продавец») и с публичной коммуникацией |

**Рекомендация:** зафиксировать один вариант. Для выбранной схемы ЮKassa-split на реквизиты организатора логичнее **«от имени и за счёт Принципала»** (или явная marketplace-формулировка ЮKassa с организатором как seller), и убрать вторую ветку из текста.

### 3.2. Незакрытая фискализация §6.2

> [разделённая фискализация: Принципал — чек на билет, Агент — на вознаграждение **/ фискализацию осуществляет Провайдер…**]

Без выбора нельзя корректно спроектировать чеки 54-ФЗ и онбординг продавцов в ЮKassa. Это нужно закрыть **до** включения `ticketSalesEnabled` в prod.

### 3.3. Плейсхолдеры

Во всех пяти файлах: `[дата]`, `[название]`, `[адрес]`, ИНН/ОГРН, контакты DPO. Для загрузки в prod БД плейсхолдеры должны быть заполнены (Policy — особенно контакт оператора).

### 3.4. Термин «Агент» vs «не продавец»

ПС и Org говорят: сервис **не продавец**. Агентский договор называет Оператора **Агентом** по реализации билетов — это нормально для агентской схемы, но только если:

- в UI/чеках/оферте покупателю ясно, кто продавец (организатор);
- деньги Принципала не смешиваются с выручкой Агента (split / раздельный учёт);
- предмет §2.1 не переключает схему в «продажа от имени площадки» без обновления ПС/Org.

Иначе возникает расхождение между витринной офертой и агентским договором.

## 4. Код vs целевая модель

| Ожидание | Факт в коде | Статус |
|----------|-------------|--------|
| Организатор = продавец | `SellerOrganizationId` на заказе; Participate при `TicketsEnabled` запрещён | ✅ модель данных |
| Комиссия сервиса | `AmountCommission` / `AmountSeller` от `payments.commissionPercent` | ✅ учёт |
| Split на реквизиты организатора | `CreatePayment` передаёт **только `Amount = amountTotal`**; payout-реквизиты org **не** участвуют в платеже; `provider_seller_id` / onboarding не используются | ❌ stub single-merchant |
| Агентский договор принят до продаж | `SetCanSellTicketsAsync` проверяет **только** `VerificationStatus == Verified`, не `TicketingAgreement` | ❌ gap |
| Feature flag | `features.ticketSalesEnabled` default `false` | ✅ безопасный default |
| Wallet ≠ билеты | Отдельный `WalletsService`; orders не трогают wallet | ✅ |

**Итог:** юридические пользовательские тексты и целевая схема владельца в целом совпадают; **агентский договор ещё с открытыми альтернативами**; **платёжный runtime пока не реализует split**, а только готовит суммы в заказе.

## 5. Рекомендуемые действия (порядок)

### Документы (юр. + продукт)

1. Закрыть §2.1 Агентского договора — один режим, согласованный с ПС §6 и Org §2.4.
2. Закрыть §6.2 — модель чеков (разделённая vs провайдер).
3. Заполнить реквизиты Оператора во всех текстах; залить актуальные версии в БД `documents`.
4. Явно описать в Агентском / Org, что расчёты идут через ЮKassa split (или эквивалент маркетплейса), комиссия удерживается при платеже.

### Код / процесс

5. Gate: `CanSellTickets=true` только при принятой актуальной `TicketingAgreement` (+ verified, как сейчас).
6. Реальный `IPaymentProvider` ЮKassa с transfers/split и привязкой `provider_seller_id` организатора.
7. Не включать `ticketSalesEnabled` в prod, пока п.1–2 и п.6 не закрыты (либо явный «технический стенд» с дисклеймером).
8. UI: не показывать ticketing CTA при выключенном флаге; не путать wallet top-up с оплатой билета.

## 6. Краткая шпаргалка для UI/поддержки

- Покупателю: «Билет продаёт организатор; EList — площадка».
- Организатору: «Чтобы продавать — верификация + агентский договор + реквизиты выплат».
- Policy — ссылка «ознакомиться», без обязательной галочки.
- Consent + Agreement — галочки / re-consent.
- Оплата тарифа сервиса — кошелёк; оплата билета — ЮKassa.
